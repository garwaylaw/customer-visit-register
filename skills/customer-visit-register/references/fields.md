# 14类高频字段的含义与更新规则

这些是语义角色，不是必须存在的固定表头。其他人可能改名、合并或拆分字段；以名称、类型、合法选项、代表性内容和用户确认的用途为准。只映射下面14类，其余列不纳入提取和填写。

| 语义角色 | 原始字段名 | 根据实际内容理解的含义 | 默认填写/更新规则 |
|---|---|---|---|
| customer_name | 客户名称 | 门店、工厂或经营主体的标识，常含“区域－位置－名称” | 检索时可拆分名称与区域；存储时不擅自更名，冲突须确认 |
| region | 地区（详细到镇） | 客户所属行政区域，实际可能混用区、镇等层级 | 匹配已有选项，信息不足不猜镇；旧值冲突明确展示 |
| cluster | 集散地名称 | 商场、建材市场、街道或客户聚集片区，比地区更具体 | 如建材城、商业街、工厂片区；不能把所有客户都强行归商场 |
| customer_type | 客户类型 | 客户经营形态及渠道类别 | 如定制工厂、卖场门店、街边门店、工作室；依据事实匹配真实选项 |
| visit_date | 拜访日期 | 表内登记的拜访时间，首次/最近/事件日期用途需核对 | 转写未特别说明日期时默认使用实际录入当天；明确提到其他日期时解析为具体日期并展示确认。最近日期不因补录旧拜访倒退；首次日期不能每次回访覆盖；日期歧义待确认 |
| visit_type | 拜访类型 | 接触客户的阶段、方式或来源 | 以目标表真实选项为准；若选项为“首次拜访／二次拜访／多次拜访”，新建客户默认首次拜访，已有一次拜访记录时填二次拜访，已有两次及以上时填多次拜访 |
| owner | 跟进人员 | 负责联系和推进客户的填表人，可能以平台账号保存 | 首次使用请用户提供其表内名称；不能默认登录人或客户方接洽人，人员字段提交前解析并核对真实用户ID |
| storefront_photo | 门头照片 | 识别门店或工厂经营场所的照片附件 | 只有实际提供且明确关联客户的照片才拟上传；转写不产生照片；默认保留旧附件 |
| visit_history | 拜访信息（每次更新） | 本次沟通过程、客户反馈、合作障碍、进展与后续安排 | **仅在完整原文后追加**本次已确认记录，保留关键产品、数字、条件、异议和承诺 |
| general_notes | 文本 | 客户综合情况和详细备注，偏客户背景、经营状况、采购习惯及沟通详情 | 与拜访信息有重叠，不能认定一定是首次拜访；默认仅补充明确的新背景事实，保留旧文，不用本次纪要覆盖 |
| intention | 意向程度 | 在原表实际是“单品合作／全品合作／拒绝合作”，表示合作范围或态度 | 别的表可能是高/中/低；按实际选项重新理解。“很感兴趣”不能映射为全品合作 |
| interested_products | 意向产品 | 客户明确表示兴趣、考虑试用或进一步了解的产品/品类 | 默认按真实选项ID合并去重；介绍过不等于感兴趣，意向不等于已下单 |
| materials | 物料 | 与客户相关的宣传、展示和销售辅助物料 | 如图册、量尺本、展示板、展示盒；先核实是已送还是计划，不能把“下次带”写成“已投放” |
| competitors | 竞品品牌 | 客户在用、经营或沟通中提及的其他品牌及供货类型 | 区分在用/曾用/比较；实际选项可能包含工厂自配、非品牌，不能当独家合作；默认合并去重 |

## 名称和内容冲突

先展示冲突并询问。例如列名“意向程度”，但选项表达合作范围；以确认的业务语义填写，不能用名称字面含义强行解释。只读列只用于理解，不提交修改。

多个字段承载同一角色时确认分工。“客户背景”与“拜访日志”不能每次重复填相同长文；若用户仅有一个综合备注列，可将本次内容追加到该列，保留已有内容，无需新建字段。

如果没有任何可存放拜访历史的字段，先输出完整追加草案并请求用户指定位置。用户可确认只填其余字段，但必须标明拜访文字未入表。

## 值与选项

- 未提及不生成变更；空白不等于否定；原值不是空时不得因提取缺失而清空。
- 拜访日期是例外：转写没有日期信息时，确认方案默认填写执行录入操作当天的本地日期，并明确标注为默认值。不能用转写日期、文件修改时间或模型知识截止日期代替实际录入当天。
- 明确取消某个意向产品或停用品牌时，在确认单展示移除项；非历史字段的清空/移除必须专项说明并确认。
- 单选只能取合法选项，多选按ID去重并保留原顺序。产品同音纠错和缩写需要证据，歧义时提供候选。
- “首次拜访／二次拜访／多次拜访”表示该客户的累计拜访阶段。只有完整查重后确认客户不存在，才可把首次建档默认标为“首次拜访”；已有客户须结合其完整拜访历史判断次数，无法可靠计数时在确认单中标记待确认。
- 没有对应选项时不自动新增选项，可将事实留在本次拜访文字中，说明该结构化字段暂不填写。
- 人员和附件用平台实际ID。关联照片上传、负责人变化等动作纳入本次确认单。
- 从转写中提取的 `=` 开头内容按文字写入，不能作为电子表格公式执行。

## 追加样式

沿用原表稳定格式，或建议：

```
【2026-09-25｜李明｜多次回访】
沟通过程：……
客户反馈：……
后续安排：……
```

这几个段落只是拜访历史内部的文字结构，不是新增字段。只写转写有依据的内容；不清楚日期/人员就先询问或在确认稿注明未知，不虚构。允许去口头重复，但不能省略重要条件或把推测改成确定事实。

追加时以完整旧值为前缀，只在必要时增加分隔换行；不先对旧文执行去空白或重排。超过平台长度限制时停止该字段写入并说明，不截断旧文或新片段。
