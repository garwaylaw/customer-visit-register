# 用户确认、提交和恢复

## 确认单必须具体

每客户给出：

```
方案ID / 修订号
目标：平台、文件、工作表
客户：名称、记录ID或唯一身份组合
拟操作：新增/更新
匹配依据和检索完整性
字段 | 旧值 | 拟写入值/追加片段 | 更新策略 | 证据或待确认点
本次追加拜访全文：……
未写入信息及原因：……
```

首次同时展示字段映射。历史旧文很长时可展示尾部及长度，但内部读取/拼接必须使用完整原文。不能请用户批准未展示的额外改动。

明确请求对客户身份及本次方案确认，等待回复后才写入。可部分批准客户/字段，未确认的保留草案。用户修改事实后生成修订版；用户准确指定修改并明确要求提交时可接受该修订确认。结构性变化、不同客户或新增动作不能继承原批准。

审批只来自对话用户。配置的 confirmed 标记只表示映射已确认，不是业务写入授权。跨会话有本地approved=true但没有可验证的用户审批上下文时，重新展示并确认。

## 本地计划与幂等

在 `.customer-visit-register/` 保存必要配置、计划、受影响字段快照、批准范围及执行日志，不保存凭据，不把运行资料放进skill包。摘要可用规范化JSON的SHA-256绑定计划版本；摘要不是审批。

事件重复检查以目标表、客户身份、明确拜访日期（若有）和规范化转写摘要为依据。日期缺失时不能每次用运行日期重新生成事件。优先利用已有平台幂等能力；否则结合本地提交日志和目标历史片段核验。不擅自新建标记列，不静默将技术编号写入客户备注。

同一天可能有多次拜访，日期相同不能直接去重；转写略改也不代表新事件。存在歧义时询问。

## 写入前重读

核对schema、稳定客户ID和受影响字段的当前完整值。新增前再次检查客户及本批已创建记录，避免并发重复建档。

- 旧历史仍为完整前缀，只是他人追加了新内容：保留最新历史再追加已批准片段。
- 旧历史被编辑、删除或无法完整读取：暂停该客户并重新确认，不覆盖。
- 单值字段变化或多选当前值不同于批准时：展示新旧差异并重新确认，不丢失他人修改。
- 追加片段/事件已存在：核对是否本次操作已成功，不再次追加。
- 同一客户多次事件：依次基于最新完整内容构建，避免后一步覆盖前一步。

优先用版本条件更新/事务。没有原子更新时“先读后写”仍有竞态，不能宣称彻底避免冲突；检测到活跃修改就停止覆盖式更新。

## 执行与核验

只提交批准字段，未提到字段不得以null/空字符串送出。文字按文字写入，避免被识别为公式。上传附件也应是确认单内的明确动作。

遇到超时或返回不明，先查稳定ID、客户身份和本次追加片段。已成功则不重试；确定未成功且批准仍有效才重试；无法判定则报告“结果未知”。不通过再建一条记录来试探。

创建成功后保存新ID；随后追加失败时仅处理未成功部分。多客户或分步操作没有事务时允许部分成功，但必须逐项报告，不自动删除、清空或回滚。

回读核验所有已批准变更，包括历史完整前缀和本次片段。格式变化按语义值/选项ID判断。报告：已写入并核验 / 部分成功 / 未核验 / 结果未知 / 待处理；附记录链接（若有）。本地副本结果不得称云端原表已更新。
